## テーマ1 — 規模を入れて壊れ方を見る

**目標**: Day 13 のベンチは2万件だった。桁を上げて、LSM の性能特性と**限界**を自分の数字で見る。

**やること**
- 100万件を流し込む。`(time (dotimes [i 1000000] (put store (format "key%08d" i) (str "value" i))))`
- ディレクトリを `ls -la` して、SSTable の **tier（サイズの階層）** が育っているのを眺める。
- `get`（1件）/ `scan`（範囲）の速さ、`stats` の読み込み増幅を測る。
- パラメータを振り直す：`:flush-threshold` / `:compaction-threshold` / `:wal-fsync`。
- **上位 tier のマージが重くなる**のを観察する（既知の制約＝コンパクションの全メモリ実体化）。メモリ使用量も見る。

**チェックポイント**
- [ ] 100万件の put にかかった時間と、SSTable の枚数・階層が分かった
- [ ] 100万件から1件引く速さ、範囲取得の速さが手元にある
- [ ] コンパクションが重くなる規模の感覚を掴んだ

## テーマ2 — キー設計でソート順を機能にする（時系列ログ）

**目標**: **キーの並びが、そのまま機能になる**という LSM の核心を手で作る。

**やること**
- キーを `event:<timestamp 13桁ゼロ埋め>:<id>` にして、数十万件のイベントを流し込む。

```clojure
(put store (format "event:%013d:%s" (System/currentTimeMillis) (random-uuid))
           (pr-str {:type :login :user "aki"}))
```

- 「直近1時間のイベント」を `scan` 一発で取得する。

```clojure
(scan store (format "event:%013d:" (- now 3600000))
            (format "event:%013d:" now))
```

- **前方一致検索**を書く。

```clojure
(defn prefix-scan [store prefix]
  ;; [prefix, prefix+1) の範囲 = prefix で始まる全キー
  (scan store prefix (str prefix (char (inc (int (last prefix)))))))
```

- ゼロ埋めが必要な理由を確認する（文字列の辞書順を数値順に一致させるため）。試しにゼロ埋めなしにして壊れ方を見る。

**チェックポイント**
- [ ] 時刻範囲のイベント取得が `scan` 一発でできる
- [ ] 前方一致検索が動く
- [ ] 「キー設計でソート順を作り、範囲取得に使う」感覚が言語化できる

## テーマ3 — テーブルを KV に載せる

**目標**: KV の上に「表」を立ち上げる。MyRocks / CockroachDB がやっていることを手で再現する。

**やること**
- キーのエンコード規約を決める（例）：

```
主キー行       : "t:users:0:<id ゼロ埋め>"   → value = 行データ（pr-str）
セカンダリ索引  : "t:users:1:<email>:<id>"    → value = ""（空）
```

- ラッパーを書く（数十行）：
  - `insert-row!` … 主キー行 + セカンダリ索引の両方を put
  - `find-by-pk` … 主キーの point get
  - `find-by-email` … **索引を引いて id を得て、主キーをもう一度 get**（2段引き）
  - `range-query` … `WHERE id BETWEEN a AND b` を `scan` で
  - `delete-row!` … 主キー行と索引の両方を delete
- 索引と行の整合性が崩れるケースを試す（`delete-row!` の途中で落ちたら？）。

**チェックポイント**
- [ ] 主キー検索・セカンダリ索引検索・範囲検索の3つが動く
- [ ] セカンダリ索引が「2回引いている」ことを自分の言葉で説明できる
- [ ] 索引の整合性維持が辛い（＝トランザクションが欲しい）と実感した

## テーマ4 — RESP サーバ（redis-cli から繋ぐ）

**目標**: **既存のクライアントツールが、自分の DB に繋がる**状態を作る。

**やること**
- `java.net.ServerSocket` で TCP を待ち受ける。
- Redis プロトコル（RESP）の `GET` / `SET` / `DEL` を実装（余裕があれば `SCAN`）。3コマンドなら TCP サーバ込みで100行程度。
- `redis-cli -p 6380` で接続して叩く。

```
$ redis-cli -p 6380
127.0.0.1:6380> SET user:1 aki
OK
127.0.0.1:6380> GET user:1
"aki"
```

- サーバを再起動してもデータが残ることを確認する（WAL / SSTable が効いている）。

**チェックポイント**
- [ ] `redis-cli` から SET / GET / DEL ができる
- [ ] 再起動してもデータが残っている
- [ ] README に「Redis 互換の最小サーバ」として書ける

## テーマ5 — 転置インデックスのプロトタイプ

**目標**: 「**SSTable + Bloom filter は検索エンジンの索引にそのまま使えるか？**」に自分で答えを出す。

**やること**
- 小さな文書集合（数百件）を転置する。

```
key = "term:<語>"   value = posting list（文書ID列をエンコード）
```

- 実装するもの：
  - 単語検索（`get "term:clojure"` → 文書ID列）
  - **AND 検索**（2つの posting list の積集合）
  - **前方一致**（`scan "term:cl" "term:cm"` → `cl` で始まる全語）
- 課題を洗い出す：
  - posting list の**更新**をどうするか（今のエンジンは値の上書きしかできない。追記型にするには？）
  - value が大きくなる語（数万文書に出現）に、今の SSTable 形式は耐えるか
  - スコアリング（TF-IDF）に必要な情報をどこに置くか
- **何を Go / Rust に移植すべきか**をメモにまとめる。

**チェックポイント**
- [ ] 単語検索・AND 検索・前方一致が動く
- [ ] 「SSTable をそのまま転置インデックスに使えるか」に自分の答えが出た
- [ ] 次のプロジェクト（全文検索エンジン）の設計方針が言語化できた
