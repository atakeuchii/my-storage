# LSM-tree ストレージエンジン自作カリキュラム（Clojure / 2週間）

> **ゴール**: LevelDB / RocksDB の簡易版を Clojure で実装し、「DBが実際にどうデータを保存・取得しているか」を手で理解する。
> **対象**: DBエンジニアとして検索・収集を担当しているが、ストレージ層の内部実装は外から使う側だった人。
> **想定時間**: 平日 2〜3h + 週末多め、ゆるく14日。早ければ10日でも回せる構成。

---

## なぜこれをやるのか（最初に読む）

普段あなたが「使う側」にいる DB は、内部でだいたい次のことをやっている：

1. 書き込みは**まずログに追記**（落ちても消えないように）
2. **メモリ上のソート済み構造**にためる
3. たまると**ディスクにソート済みファイル（SSTable）として書き出す**
4. 読み込みは**メモリ → 新しいファイル → 古いファイル**の順で探す
5. ファイルが増えすぎたら**マージして整理する（コンパクション）**

この5つを自分で書くと、「なぜ書き込みは速いのに読み込みにはBloom filterが要るのか」「なぜ削除がすぐ消えずtombstoneになるのか」「なぜ本番DBがあの挙動をするのか」が腹落ちする。シニアとそれ以外を分けるのはまさにここ。

### Clojure でやる旨味（意識して使う）

- **memtable = `(atom (sorted-map))`**。イミュータブルなので「今のmemtableをスナップショットしてSSTableに書き出しつつ、新しいmemtableに書き込みを続ける」が **ロックなしのアトミックなswapで書ける**。本来コピーオンライトを自前で組む面倒な箇所がタダで手に入る。
- **コンパクション = ソート済みシーケンスのk-wayマージ**。Clojureのlazy seq / reduce のど真ん中。
- **永続化 = `java.nio`（FileChannel / ByteBuffer）** にフルアクセスできる。JVMの資産がそのまま使える。
- **テスト = `test.check`** で「自作エンジン vs 素の `sorted-map`」の等価性をプロパティ検査。これが最高に効く。
- 唯一の摩擦はSSTableのバイナリエンコード。ホットパス以外は `DataOutputStream` 直叩き or nippy で十分。

## 全体アーキテクチャ

```
            put / get / delete
                  │
                  ▼
        ┌───────────────────┐
        │  WAL (append-only) │  ← まずここに追記して fsync（耐久性）
        └───────────────────┘
                  │
                  ▼
        ┌───────────────────┐
        │  Memtable          │  ← (atom (sorted-map)) メモリ上のソート済み
        │  (sorted-map)      │
        └───────────────────┘
                  │ 閾値超えでflush
                  ▼
   ┌──────────┬──────────┬──────────┐
   │ SSTable  │ SSTable  │ SSTable  │  ← イミュータブルなソート済みファイル
   │ + index  │ + bloom  │ + bloom  │     新しい順に探す
   └──────────┴──────────┴──────────┘
                  │ 増えたらマージ
                  ▼
            Compaction（k-way merge / tombstone除去）

read path: Memtable → (flush中のimmutable memtable) → SSTable新→古
```

### Day 2 — WAL（Write-Ahead Log）

**目標**: プロセスが落ちても直近の書き込みが消えない状態を作る。

**やること**
- 追記専用ファイルを開き、`put`/`delete` のたびに**レコードを追記して fsync**。
- レコード形式を決める（例）：`[key長(4byte)][key][value長(4byte) or tombstone印][value][crc(任意)]`。
- 書き込み順序を厳守：**WALに書いてfsync → それからmemtableに反映**。

**概念**
- 「ログ先行書き込み」がなぜ耐久性を担保するか。fsyncのコストと、それでも書き込みが速い理由（シーケンシャル追記）。

**Clojureヒント**
- `java.io.DataOutputStream`（`writeInt` / `write`）で素直に書ける。
- fsync は `FileChannel#force(true)` or `FileDescriptor#sync`。毎回 force すると遅いので「まずは毎回force、後でグループコミットを検討」とコメントを残す。

**チェックポイント**
- [ ] putするとWALファイルが伸びる
- [ ] レコード形式をバイト単位で図に書けた

---

### Day 3 — WAL リプレイとクラッシュ回復

**目標**: 起動時にWALを読み直して memtable を復元する。**ここで初めて「DBっぽさ」が出る。**

**やること**
- 起動時にWALを先頭から読み、レコードを順に memtable へ適用。
- 壊れた末尾レコード（書き込み途中で落ちたケース）を**安全に切り捨てる**処理（長さ/CRCで検出）。
- **回復テスト**：putを数件 → プロセス相当の状態を捨てる → 新インスタンスでWALリプレイ → getできることを確認。

**概念**
- partial write / torn write をどう扱うか。なぜ末尾だけ壊れる前提で良いか。

**Clojureヒント**
- リプレイは「ファイルをレコードのlazy seqに変換 → reduce で sorted-map を畳む」と綺麗に書ける。EOF/破損で seq を打ち切る。

**チェックポイント**
- [ ] 「書く→捨てる→リプレイ→読める」が通る ← **最初の大きな達成感ポイント**
- [ ] 末尾破損を入れても起動が落ちない

### Day 4 — Memtable 抽象化と flush トリガ

**目標**: memtable がたまったらディスクに退避する仕組みの「制御部分」を作る。

**やること**
- memtable のサイズ（件数 or 概算バイト数）を追跡し、閾値超過で **flush をトリガ**。
- flushの肝：**現在のmemtableをアトミックにスナップショットして新しい空memtableに切り替える**。flush中の古いmemtableは「immutable memtable」として読み込みパスから見える場所に退避（リストやvectorで保持）。
- flushが終わったら対応するWALを切り替え/ローテート。

**概念**
- なぜ切り替えが必要か（flush中も書き込みを止めない）。Clojureのイミュータビリティでここがどれだけ楽になるか体感する。

**Clojureヒント**
```clojure
;; 概念イメージ：原子的に「古いmemtableを取り出しつつ新しい空に差し替える」
(let [old (atom nil)]
  (swap! state (fn [s]
                 (reset! old (:memtable s))
                 (assoc s
                        :memtable (sorted-map)
                        :immutables (conj (:immutables s) @old))))
  @old) ;; これをSSTableへ書き出す
```
（実装方針はあなたの設計次第。要は「読み込みが古いmemtableを取りこぼさない」こと）

**チェックポイント**
- [ ] 閾値を小さくすると flush がトリガされる
- [ ] flushトリガ中もputが受け付けられる（取りこぼさない）

### Day 5 — SSTable ライター

**目標**: ソート済み memtable を、再読み込み可能なファイル形式でディスクに書く。

**やること**
- SSTableファイル形式を設計：
  - **データ部**：ソート済みの `[key][value]` を連続で
  - **スパースインデックス**：N件ごと（or Nバイトごと）に `key → ファイルオフセット` を記録
  - **フッター**：インデックス開始オフセット、（後で）Bloom filterオフセット、マジックナンバー、エントリ数
- memtable（or immutable memtable）を走査してこの形式で書き出す。

**概念**
- なぜ**スパース**インデックスで足りるのか（データがソート済みだから、近いオフセットへ飛んで線形スキャンすればよい）。フルインデックスとの容量トレードオフ。

**Clojureヒント**
- 書き出しは `sorted-map` を seq で順に流すだけなので超素直。
- オフセット管理のため「今何バイト書いたか」を数えながら書く（`CountingOutputStream` 相当を自作 or カウンタを持つ）。

**チェックポイント**
- [ ] SSTableファイルが1つ生成される
- [ ] フッター→インデックスの逆引きで、ファイル末尾から構造をたどれる設計になっている
- [ ] **フェーズ1完了**：書き込みは「WAL→memtable→SSTable」の流れが一通り通った

## フェーズ2：読み込みパス（Day 6–9）

### Day 6 — SSTable リーダー（ポイントルックアップ）

**目標**: 書いたSSTableから単一keyを引けるようにする。

**やること**
- フッターを読む → スパースインデックスをロード → 目的keyの**直前のオフセット**へシーク → そこから線形スキャンしてkeyを探す。
- `get` の探索順を更新：**memtable → immutable memtables → SSTable（新しい順）**。

**概念**
- 「新しいものが勝つ（newest wins）」の原則。同じkeyが複数SSTableにあったら新しい方を採用。
- 読み込み増幅（read amplification）の芽：SSTableが増えるほど最悪何ファイル見るか。→ Day7のBloom filterへの伏線。

**Clojureヒント**
- `java.nio.channels.FileChannel` の `position` + `read(ByteBuffer)` でシーク読み。mmap（`map`）にしてもよいが、まずはシークで素直に。

**チェックポイント**
- [ ] flush済みデータ（memtableにもうない）をSSTableから get できる
- [ ] 同じkeyを更新→flushを2回して、新しい値が返ることを確認

---

### Day 7 — Bloom filter

**目標**: 「このSSTableにkeyが**無い**ことを高速に判定」してファイルアクセスを減らす。

**やること**
- `java.util.BitSet` + k個のハッシュでBloom filterを実装。SSTable書き出し時に全keyを登録し、フッター近くに保存。
- `get` で各SSTableを見る前に `mightContain?` をチェックし、`false` なら**そのファイルは丸ごとスキップ**。

**概念**
- 偽陽性はあるが偽陰性はない、という非対称性がなぜ「スキップ判定」に使えるか。
- ハッシュはダブルハッシュ（Kirsch-Mitzenmacher：`h1 + i*h2`）で k本を1〜2個のハッシュから合成すると省コスト。

**Clojureヒント**
- ハッシュは `clojure.lang.Murmur3` or `(.hashCode ...)` を2本使って合成。ビット数とk本数は `n` と目標偽陽性率から計算（式はDDIA/Wikipedia）。

**チェックポイント**
- [ ] 存在しないkeyのgetで、Bloom filterによりSSTableアクセスが減っていることをログで確認 ← **効果が目で見える達成感**
- [ ] 偽陰性が起きない（存在するkeyは必ず通る）ことをテスト

### Day 8 — 複数SSTableとマニフェスト

**目標**: SSTableが何枚もある状態を正しく管理する。

**やること**
- どのSSTableがどの順序（世代/レベル）かを記録する **マニフェスト**（単純なEDNファイルでOK）。
- 起動時：マニフェストを読んで既存SSTable群を認識 → WALリプレイで未flush分を復元。
- `get` / レンジが「全SSTableを新しい順に、Bloom filterで枝刈りしつつ」見るように整理。

**概念**
- なぜメタデータ（どのファイルが有効か）を別管理するか。コンパクションでファイルが入れ替わる前準備。

**チェックポイント**
- [ ] 再起動してもSSTable群＋未flush分が正しく復元される
- [ ] 複数SSTableにまたがるデータが一貫して読める

### Day 9 — 削除（tombstone）とレンジスキャン

**目標**: 削除を正しく扱い、ソート済みの強みである範囲取得を実装する。

**やること**
- `delete` は物理削除せず **tombstone（削除マーカー）を put** する。memtable / WAL / SSTable すべてでtombstoneを表現できるようにする。
- `get` は「新しい順に見て、最初に当たったのがtombstoneなら『無い』を返す」。
- レンジスキャン `scan(start, end)`：memtable + 全SSTableの**ソート済みイテレータをk-wayマージ**し、同一keyは新しい方を採用、tombstoneは結果から落とす。

**概念**
- なぜ削除が即座に消えないのか（古いSSTableにまだ実体が残っているから、tombstoneで「上書き」する必要がある）。これが「削除したのに容量が減らない」現象の正体。

**Clojureヒント**
- k-wayマージはmin-heap or `clojure.data.priority-map` で。あるいは各イテレータの先頭を比較するlazyな実装。Clojureのlazy seqと相性が良い。

**チェックポイント**
- [ ] put→delete→get で「無い」が返る（しかも古いSSTableに実体が残っていても）
- [ ] scanがソート順で、削除済みを除いて返る
- [ ] **フェーズ2完了**：読み込みパスが本格的になった

## フェーズ3：コンパクション & 仕上げ（Day 10–14）

### Day 10 — コンパクションの基礎（2ファイルのマージ）

**目標**: 増えたSSTableを1つにマージし、無駄を削る根幹を作る。

**やること**
- 2つのSSTableを **k-wayマージ**して新しいSSTableを1枚作る：
  - ソート順にマージ
  - 同一keyは新しい方を採用
  - **最下層なら tombstone と被削除エントリを物理的に捨てる**
- 完了後マニフェストを更新し、古い2枚を削除。

**概念**
- compaction が「読み込み増幅」と「空間増幅」を同時に下げる仕組み。マージ中も読み書きを止めない（新ファイルを作ってから差し替える）設計。

**チェックポイント**
- [ ] 2枚→1枚にマージできる
- [ ] マージ後、削除済みデータが本当に消えている（容量が減る）← **tombstoneの伏線回収**

---

### Day 11 — コンパクション戦略とトリガ

**目標**: 「いつ何をマージするか」のポリシーを入れる。

**やること**
- まずは **size-tiered**（似たサイズのSSTableがN枚たまったらまとめてマージ）を実装。トリガ条件を決める。
- 余裕があれば **leveled**（L0/L1/L2…、各レベルにサイズ上限、あふれたら下のレベルへマージ）の考え方をメモ or 簡易実装。
- コンパクションをバックグラウンドで回す（別スレッド / `future`）か、明示トリガで回すかを決める。

**概念**
- size-tiered（書き込み有利・空間効率悪め）vs leveled（読み込み/空間有利・書き込み増幅大）のトレードオフ。**これは実務でDBチューニングする時に直結する知識**。

**Clojureヒント**
- バックグラウンド化は `future` + ロック最小化で。マニフェスト更新だけを直列化すれば、マージ本体は並行でも安全に設計できる。

**チェックポイント**
- [ ] 大量putでSSTableが増え、自動でコンパクションが走り枚数が減る
- [ ] size-tiered と leveled の違いを自分の言葉で説明できる

### Day 12 — プロパティベーステスト（ここで品質が跳ねる）

**概念**

## ストレッチ目標（2週間で終わって余ったら）

- **ブロックキャッシュ**：SSTableのデータブロックをLRUでキャッシュ。
- **圧縮**：データブロックを Snappy / LZ4 で圧縮（rocksdbと同じ方向）。
- **MVCC / スナップショット読み取り**：シーケンス番号を付けて「ある時点の読み取り」を実現。Clojureのイミュータビリティと相性◎。
- **leveled compaction を本実装**：L0〜Lnのレベル管理。
- **2本目の検索エンジンへ接続**：ここで作ったSSTable + Bloom filterを、次に作る全文検索エンジンの**オンディスク転置インデックス**に流用する（Luceneも自前ストレージ層を持つ）。
